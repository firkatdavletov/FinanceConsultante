# Firebase T10 — вступление и участники семейного бюджета

## Настройка

Нужен JAR с Flyway V27. Сохраняются MOBILE_API_ENABLED=true,
FIREBASE_AUTH_ENABLED=true, существующий Firebase project ID и ADC вне репозитория.
Новых credentials и переменных окружения нет. Production-развёртывание отдельно.

V27 добавляет в firebase_budget_invitation accepted_by_uid и accepted_member_id:
receipt успешного принятия. Старые UUID, финансовое авторство, очереди и receipts
не изменяются. Для существующих приглашений V26 поля receipt остаются NULL;
ранее использованный код без receipt не предоставляет новое членство.

## HTTP-контракт

Каждый endpoint проверяет Firebase ID token до DB-транзакции. Статический токен
не допускается. Ответы имеют Cache-Control: no-store.

- POST /api/v4/budgets/invitations/accept, тело `{code}` → 200
  `{id,name,memberId,role}`. Пользователь создаётся по проверенному UID, если его ещё нет.
- GET /api/v4/budgets/{budgetId}/members → 200
  `{budgetId,members:[{id,name,role,joinedAt,currentUser}]}`. Только активные участники
  выбранного бюджета, OWNER первым. UID и email других пользователей не выдаются.
- DELETE /api/v4/budgets/{budgetId}/members/{memberId} → 204, только OWNER.
  OWNER нельзя отозвать. Отсутствующий, чужой или уже отозванный MEMBER не изменяется.

Неверный/отозванный Firebase token даёт 401; отсутствие членства или прав — 403.
Непригодный код даёт 409 invalid_invitation без различения причины.
OWNER, принимающий приглашение собственного бюджета, получает 409 already_member;
код остаётся неиспользованным. MEMBER может создавать доходы и расходы через
существующие адресные v4 endpoints; настройки бюджета и управление доступом требуют OWNER.

## Принятие и повтор

Код нормализуется: максимум 80 введённых символов, пробелы/дефисы удаляются,
регистр повышается, остаются ровно 20 символов Crockford Base32. Хеш вычисляется
по канонической записи из четырёх групп по пять. Plaintext в БД/логи не записывается.

Принятие блокирует household, затем строку приглашения FOR UPDATE. Так оно
сериализовано с созданием/отзывом кода T09 и конкурирующими принятиями. Проверка
срока, создание MEMBER, привязка UID и расходование кода выполняются одной транзакцией.
Один UID имеет одну текущую привязку к каждому household, но может иметь много бюджетов.
Действующее MEMBER-членство используется повторно без создания второго участника.

После потерянного ответа тот же UID и тот же активный memberId получают прежний
результат. Такой receipt можно прочитать и после TTL: нового доступа он не даёт.
Другой UID, отозванное членство и сменившийся memberId receipt использовать не могут.
Новый код после отзыва создаёт новый UUID MEMBER и обновляет firebase_budget_access;
старая история остаётся на исходном участнике, старые command payload с прежним
memberId отклоняются. Истёкший неиспользованный код (включая точную границу expiresAt),
отозванный код и использованный другим UID не дают доступа.

## Отзыв и финансовые транзакции

FirebaseBudgets удерживает shared locks активного вызывающего участника и привязки
на время адресной транзакции. Отзыв обновляет строку целевого MEMBER; UPDATE ждёт
завершения уже выполняющегося финансового запроса. После фиксации revoked_at новые
чтения, синхронизация, команды и список участников этого MEMBER получают отказ.
Существующие проводки и авторство остаются. reports_enabled выключается и очередь
отчётов участника останавливается в той же транзакции.

Отзыв не берёт household FOR UPDATE: это предотвращает обратный порядок блокировок
с финансовыми запросами, уже удерживающими member и обновляющими счёт/household.
Принятие читает членство без member FOR UPDATE под блокировкой household, чтобы
не создавать цикл с shared lock OWNER при управлении приглашениями T09.

Android при повторном приглашении загружает новый профиль полностью, затем атомарно
архивирует старый. Старые неотправленные команды сохраняются, но не переадресуются
новому memberId. Интерфейс восстановления такой архивной очереди — вне T10.

## Проверки

`./gradlew test check bootJar` выполнен успешно: 315 unit и 293 integration-теста,
без ошибок и пропусков; ktlint, Detekt, JaCoCo и bootJar прошли.

Шесть FirebaseFamilyBudgetTests используют настоящий PostgreSQL 17.11/Testcontainers
и fake Firebase verifier. Проверены общий доход/расход, собственный бюджет рядом
с семейным, роли и scoped GET, повтор после потери ответа, конкурирующие принятия,
срок/отзыв/использованный код, повторное вступление с новым memberId, отказ прежним
payload, ожидание отзыва до commit финансовой транзакции и сохранность V26→V27.

Ручная приёмка: OWNER создаёт код T09; второй Google-аккаунт принимает его в Android,
переключается между собственным и семейным бюджетами и отправляет расход; OWNER
получает изменение и отзывает MEMBER, после чего новые запросы второго устройства
отклоняются. Реальный Firebase/Google и обновлённый тестовый сервер проверяются
отдельно от автоматических фикстур. Деплой автоматически не выполнялся.
