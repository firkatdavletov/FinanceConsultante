# T05 — существующий бюджет через Firebase

Новое подключение Fillin использует только v4 по уточнению пользователя от 2026-10-21.
HTTP v1–v3 и адаптация старых очередей не входят в эту задачу. Данные не удаляются;
несовместимая очередь останавливает обмен с явной ошибкой на клиенте.

## Настройка

Развернуть текущий JAR с миграциями V24–V27. Сохранить существующие Firebase Admin credentials
вне репозитория и Android. В дополнение к Firebase project ID и ADC задать:

```dotenv
FIREBASE_AUTH_ENABLED=true
FIREBASE_LEGACY_UID=<точный UID из Firebase Authentication → Users>
FIREBASE_LEGACY_MEMBER_ID=<UUID прежнего активного участника>
```

UID — не email, не Telegram ID и не server UUID из `firebase_user.id`.
`memberId` уже существует в таблице `member`; создавать новый для миграции не нужно:

```sql
SELECT id AS member_id, household_id, role FROM member WHERE revoked_at IS NULL;
```

При нескольких строках выбрать участника нужного бюджета, не первую строку автоматически.
Нужно указать обе переменные либо оставить обе пустыми. Первый запрос настроенного UID
после успешной проверки Firebase связывает его с этим member. Пара не выводится из email,
тела запроса или Android-конфигурации. Повтор безопасен; другой UID не перехватывает member.
Пустая настройка не выдаёт существующий бюджет новым пользователям. Ошибка привязки
возвращает безопасный 503; исправить серверную конфигурацию, не создавать нового участника.

Мобильный API должен быть включён (`MOBILE_API_ENABLED=true`, как в существующей установке).
Настройка прежнего статического API остаётся до T12, но новые scoped endpoints принимают
только Firebase ID token и не имеют fallback на статический токен.

## Контракт

Все ответы запрещают HTTP-кэширование. Авторизация: `Authorization: Bearer <Firebase ID token>`.

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/v4/budgets/import` | Импорт исходного локального bootstrap с прежними UUID |
| POST | `/api/v4/budgets` | Создание первого бюджета, OWNER и начальных данных по requestId |
| GET | `/api/v4/budgets` | Массив `{id, name, memberId, role}` для текущего UID |
| GET | `/api/v4/budgets/{budgetId}` | `{scope}` прежнего бюджета |
| GET | `/api/v4/budgets/{budgetId}/sync/changes` | Страницы v4; параметры `cursor`, `limit` |
| POST | `/api/v4/budgets/{budgetId}/sync/commands` | Прежняя v4-команда и receipt |

Токен проверяется до DB-транзакции. Затем сервер выбирает `BudgetActor` по проверенному UID
и budgetId, проверяет `revoked_at` и блокирует строки членства на время транзакции.
401 — неверный/отозванный Firebase token; 403 — нет активного членства; 409 `scope_changed` —
household/member команды не совпадает с выбранным бюджетом. Повтор requestId с прежним
payload возвращает прежний receipt; изменённый payload даёт `idempotency_conflict`.
Суммы, UUID, авторство и расчёт fingerprint остаются прежними.

V24 добавляет название бюджета и таблицу связи с FK/unique. Автоматической выдачи доступа
при миграции нет. Один UID может иметь несколько бюджетов; один memberId связан с одним UID.
В T06 добавлено создание нового Firebase-бюджета; отдельная регистрационная форма не нужна.

- `./gradlew check bootJar` успешен: 315 unit и 281 integration-тестов, без пропусков.
- Реальный PostgreSQL 17.11/Testcontainers, ktlint, Detekt, JaCoCo и JAR успешны.
- Проверены явный UID/member, отсутствие доступа у аккаунта с тем же email, отзыв MEMBER,
  неправильный household команды, повтор после потери ответа, несколько бюджетов одного UID,
  сохранение прежних UUID/account/token binding при миграции и отсутствие автоматических связей.
- HTTP-тесты используют stub Firebase verifier; настоящий Admin SDK и Google-вход проверены
  отдельно в T03. Сквозная приёмка T05 с настоящим аккаунтом и обновлённым сервером остаётся
  отдельной проверкой. Production-развёртывание и изменение production данных не выполнялись.

На устройстве после развёртывания и настройки: «Облако» → Google-вход → обновить список →
выбрать прежний бюджет → сверить баланс/историю → добавить расход → синхронизировать.
Другой Google-аккаунт не должен видеть этот бюджет; возврат исходного восстанавливает его данные.


## Создание бюджета T06

Основной `POST /api/v4/budgets` принимает только Firebase ID token, без fallback на статический токен.
Все денежные поля — строки, UUID бюджета/member/категорий выдаёт сервер:

```json
{
  "requestId": "11111111-1111-4111-8111-111111111111",
  "name": "Тестовый бюджет",
  "openingBalance": "1234.50",
  "accountingStartedOn": "2026-10-20",
  "currency": "KZT"
}
```

Ответ 200 `{id, name, memberId, role: "OWNER"}` пригоден для последующего scoped GET/changes/commands.
Название — 1–80 символов, без крайних пробелов и управляющих символов; сумма — до двух десятичных
знаков в диапазоне Money, включая ноль и отрицательные значения; дата — с года 1 по today Asia/Almaty.
Невалидная форма даёт 400. Firebase-пользователь возникает при первом подтверждённом запросе;
в теле создания нет доверенного UID, Telegram ID или отдельного пароля.

V25 добавляет таблицу receipt с PK UID/requestId, FK на членство и уникальным household.
В одной транзакции фиксируются household, OWNER, account, четыре базовые категории, членство и receipt.
Потеря ответа не создаёт дубль: исходный requestId/payload возвращает тот же бюджет.
Изменённый payload — 409 `idempotency_conflict`; новый requestId разрешает ещё один бюджет.
Блокировка ключа и PK защищают от конкурентных повторов; ошибка до commit откатывает всё.

Для сохранённого прежнего bootstrap статический POST перенесён на `/api/v4/legacy/budgets`.
Остальные статические endpoints остаются до T12. Прежние Android-сборки со статическим созданием
не используют основной путь после обновления сервера; текущая сборка обновлена согласованно.
Миграция не меняет прежние Firebase-членства и финансовые данные.

Проверены реальным PostgreSQL/Testcontainers: конкурентное создание, потерянный ответ/retry,
изменение payload, UID-изоляция, несколько бюджетов UID, rollback всех начальных данных,
валидация/ошибочные токены и миграция V24→V25 с прежним членством и балансом.
HTTP-тесты подменяют только Firebase verifier. Реальные Google-аккаунты проверяются отдельно
на обновлённом тестовом сервере; production-развёртывание этой задачей не выполняется.


## Перенос локального бюджета T07

Развернуть сервер с изменениями T07. Дополнительная миграция после V25 не требуется.
`POST /api/v4/budgets/import` принимает `{name, budget: CreateCloudBudget}` с Firebase ID token.
В `budget` передаются исходные requestId, householdId, memberId, openingBalance,
accountingStartedOn и четыре seed-категории `{id,name,kind,icon,dictionaryKey}`.
Ответ 200 `{id,name,memberId,role:"OWNER"}` сохраняет исходные идентификаторы.

Создание OWNER/счёта/категорий/членства и receipt атомарно. История и планы передаются следующими
исходными v4-командами. Один UID может иметь другие бюджеты; импорт добавляет новый и не объединяет данные.
Потерянный ответ не меняет requestId: повтор возвращает прежний бюджет. Изменённый payload — 409
`idempotency_conflict`; занятые исходные UUID — 409 `budget_identity_conflict`, без присвоения или merge.
Транзакционные блокировки исходных UUID сериализуют конкурирующие запросы даже от двух UID.
Проверены первоначальные UUID/категории, доходы/расходы/возвраты v4 и повторы receipt, конкурентный
импорт, UID-изоляция, существующий бюджет того же аккаунта, rollback и валидация bootstrap.
Автоматические HTTP-тесты используют Firebase verifier stub; production-развёртывание отдельно.

Итоговая серверная проверка T07: `test check bootJar` успешна, 315 unit и 281 integration-тест без пропусков, PostgreSQL 17.11/Testcontainers.
