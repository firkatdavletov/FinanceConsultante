# Управление Firebase-бюджетом

`PATCH /api/v4/budgets/{budgetId}` принимает `requestId` и хотя бы одно из полей
`name` или `currency`, возвращает `FirebaseBudgetSummary`. Название должно содержать
от 1 до 80 символов, без пробелов по краям и управляющих символов.

`DELETE /api/v4/budgets/{budgetId}?requestId=UUID` отправляет бюджет в бессрочный архив
и возвращает `204`. Оба метода требуют действующий Firebase ID token и роль `OWNER`.
Ответы имеют `Cache-Control: no-store`.

Архивный бюджет исчезает из каталога всех участников. Данные, синхронизация и управление
участниками по UUID возвращают `403 access_denied`. Неиспользованные приглашения отзываются,
при попытке вступления по коду возвращается `409 invalid_invitation`. Фоновая генерация
планов возобновляется после восстановления. Если синхронизация начала транзакцию до
конкурентного архивирования и PostgreSQL отклонил её снимок, сервер возвращает
`503 server_unavailable`. Следующая попытка увидит актуальное состояние бюджета.

Повтор принятого DELETE с тем же `requestId` возвращает `204` и после восстановления.
Для нового удаления нужен новый `requestId`. Изменение запроса с прежним идентификатором
возвращает `409 idempotency_conflict`. Повтор создания или импорта архивного бюджета
возвращает `409 budget_deleted` до восстановления. Импорт занятых UUID с новым
`requestId` возвращает `409 budget_identity_conflict`.

## Восстановление через поддержку

1. Убедитесь, что заявитель владеет Firebase-аккаунтом, и получите его UID по закрытому
   каналу. Используйте операторскую роль PostgreSQL с правами чтения указанных таблиц,
   обновления `household.archived_at` и выполнения `restore_firebase_budget`.
   Миграция закрывает выполнение функции для `PUBLIC`.
2. Найдите бюджет по UID владельца. Ниже используются переменные `psql`.

   ```sql
   SELECT h.id AS budget_id, h.budget_name, h.archived_at
   FROM household h
   JOIN firebase_budget_access b ON b.household_id = h.id
   JOIN member m ON m.household_id = b.household_id AND m.id = b.member_id
   WHERE b.firebase_uid = :'owner_uid' AND m.role = 'OWNER'
       AND m.revoked_at IS NULL AND h.archived_at IS NOT NULL
   ORDER BY h.archived_at DESC, h.id;
   ```

3. Уточните нужный бюджет и передайте найденные UUID и исходную дату архивации
   с полной точностью и часовым поясом. Используйте отдельную транзакцию
   `READ COMMITTED` (по умолчанию в `psql`).

   ```sql
   SELECT restore_firebase_budget(
       :'owner_uid', :'budget_id'::uuid, :'archived_at'::timestamptz
   ) AS restored;
   ```

   `true` подтверждает восстановление. При `false` запросите каталог архива заново.
   Функция проверяет действующее владение и совпадение даты под транзакционной блокировкой.
4. После обновления каталога Android покажет бюджет действующим участникам. История,
   баланс, идентификаторы и состояние синхронизации сохраняются. Для приглашения нового
   участника владелец создаёт новый код. Сервер восстановит данные, которые успели
   синхронизироваться до удаления. Локальные бюджеты и несинхронизированные изменения
   остаются вне серверного архива.

При окончательном удалении профиля владельца архивный бюджет стирается вместе с остальными
его бюджетами. Поддержка может восстановить бюджеты, архивированные после выпуска V37.
Для бюджетов, физически удалённых до V37, в базе сохранились технические отметки удаления.

## Выпуск

Разверните миграцию V37 вместе с сервером, который учитывает `archived_at`. Все обслуживающие
запросы экземпляры должны работать на этой версии до первого архивирования. Предыдущий
сервер физически удаляет бюджеты и не скрывает архивные записи. Контракт Android сохранён.
