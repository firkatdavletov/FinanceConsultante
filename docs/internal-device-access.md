# Saldomi 0.1: доступ установки к облачным функциям

Локальный бюджет открывается Android без авторизации. При обычном запуске установка делает
`GET /api/v4/app/access` с `X-Device-Id: <uuid>` и необязательным `X-App-Version: 0.1`.
ID — сохранённый UUID установки в строчном формате `8-4-4-4-12`. После переустановки
или очистки данных Android показывает новый ID в «О приложении»; старое разрешение к нему
не переносится. Проверка не отправляет финансовых данных.

| Условие | HTTP | JSON |
| --- | --- | --- |
| Активный ID | 200 | `{"mode":"INTERNAL_FULL"}` |
| Неизвестный или отозванный ID | 200 | `{"mode":"OFFLINE_FREE"}` |
| Нет ID, он повторён или неканоничен | 400 | `{"code":"invalid_device_id"}` |
| PostgreSQL недоступен | 503 | `{"code":"device_access_unavailable"}` |

Все ответы содержат `Cache-Control: no-store`. Android хранит последнее подтверждённое
разрешение в данных установки. `OFFLINE_FREE` и облачный `device_access_denied` снимают его;
ошибка сети, неуспешная проверка или незнакомый режим не меняют последнее подтверждённое
состояние. Ограничение в два локальных бюджета проверяет Android.

## Управление списком

Flyway V35 создаёт пустую таблицу `internal_app_installation`. Оператор получает UUID
по приватному каналу и выполняет параметризованный SQL после проверки нужной установки:

```sql
INSERT INTO internal_app_installation (device_id, active, label, updated_at)
VALUES (:device_id, TRUE, :label, CURRENT_TIMESTAMP)
ON CONFLICT (device_id) DO UPDATE
SET active = TRUE, label = EXCLUDED.label, updated_at = CURRENT_TIMESTAMP;
```

Отзыв:

```sql
UPDATE internal_app_installation
SET active = FALSE, updated_at = CURRENT_TIMESTAMP
WHERE device_id = :device_id;
```

После commit следующий запрос видит изменение. `label` — служебная подпись, например
«Тестовый Pixel». UUID не является средством входа: Firebase ID token, активное членство
и роль по-прежнему проверяются сервером.

## Переключатель и выпуск

`INTERNAL_DEVICE_GATE_ENABLED=false` по умолчанию. При `true` каждый запрос `/api/v4/*`
кроме `GET /api/v4/app/access`, `DELETE /api/v4/profile` и
`GET /api/v4/profile/deletion` проверяет активность ID до контроллера. Отказ возвращает
`403 {"code":"device_access_denied"}`, недоступность таблицы — 503. Запрос без ID
после включения фильтра теряет облачный доступ. Повтор уже принятой команды после
восстановления доступа сохраняет прежнюю идемпотентность. Удаление аккаунта продолжает
проверять Firebase и свежесть входа; статус доступен по прежнему `X-Deletion-Token`.

Порядок выпуска: применить миграцию и endpoint с выключенным фильтром; зарегистрировать
тестовые ID; проверить Android 0.1 с известным, неизвестным и новым ID после переустановки;
включить фильтр на тестовом сервере и проверить маршруты; выпустить Android и включить
фильтр в production после проверки собственных установок. Изменение флага требует
перезапуска сервера. Для отключения фильтра установить `false`; таблица и endpoint остаются.
