# Одноразовые правила расходов

Backend поддерживает `frequency: "ONCE"` в существующей модели правил расходов.
V32 расширяет ограничения `recurring_rule`; UUID, версии, receipts, типы событий
и версия протокола синхронизации не меняются.

## Создание и чтение

Поля создания правила:

```json
{"categoryId":"category-id","amount":"100.00","frequency":"ONCE","startsOn":"2026-11-04"}
```

Для `ONCE` поле `scheduleValue` отсутствует либо равно `null`. Число отклоняется.
Для `MONTHLY` по-прежнему обязателен день 1–31, для `WEEKLY` — ISO-день 1–7.
В ответах и sync-записях `scheduleValue` одноразового правила равен `null`
(клиент должен также принимать отсутствие поля).

Дата единственного обязательства равна `startsOn`. При создании она должна быть
не раньше начала учёта и дня создания в `Asia/Almaty`. Для прямого use case создания
днём создания служит текущая дата; для очереди — `authoredOn`.
Сам `authoredOn` ограничен началом учёта и текущим днём бюджета.
Доставка команды после `startsOn` допустима: обязательство сразу становится просроченным.
Чтение и изменение сохранённого правила не повторяют проверку даты нового правила.

Рабочий Firebase API принимает `CREATE_RULE` через
`POST /api/v4/budgets/{budgetId}/sync/commands`:

```json
{
  "requestId": "request-uuid",
  "householdId": "budget-uuid",
  "memberId": "owner-member-uuid",
  "type": "CREATE_RULE",
  "entityId": "rule-uuid",
  "authoredOn": "2026-11-03",
  "categoryId": "category-uuid",
  "amount": "100.00",
  "frequency": "ONCE",
  "startsOn": "2026-11-04"
}
```

Пример использует условные UUID. Нужны Firebase ID token и активное OWNER-членство.
Прежний `/api/v1/planned-expenses` сохраняет форму DTO и поддержку на уровне use case,
но его статическая авторизация остаётся закрытой после Firebase T12.
Эта функция не открывает устаревшие HTTP endpoints.

## Материализация и оплата

`RECURRING_RULE` возвращает `frequency: "ONCE"`, `startsOn` и nullable `scheduleValue`.
Сервер создаёт один `RECURRING_OCCURRENCE` на `startsOn` с каноническим UUID.
Android сопоставляет локальный `ruleId@date` по `(ruleId, dueOn)`, сохраняя серверный ID
и связи оплаты. Повтор `requestId` возвращает сохранённый receipt;
другой payload с тем же ключом отклоняется. Ограничение `(rule_id, due_on)` и
`INSERT ... ON CONFLICT DO NOTHING` защищают материализацию от дублей и перезаписывания.

Повторное чтение, расширение горизонта и восстановление процесса не создают новых дат
и не сбрасывают сумму, версию, оплату или статус обязательства.
Неоплаченное обязательство остаётся просроченным после своего срока.
Создание плана не создаёт ledger-расход и не уменьшает учётный баланс.

`UPDATE_RULE` без `replaceDetails: true` меняет только сумму. Полный снимок v4 может содержать поля существующего
правила, включая `ONCE` и прошедший `startsOn`. Как и для регулярных правил, изменение
суммы затрагивает только неоплаченные обязательства со сроком не раньше `authoredOn`
(текущего дня для прямого API). Уже оплаченные и просроченные обязательства сохраняются.
Удаление деактивирует правило и отменяет будущие обязательства по прежнему контракту;
прошлая и оплаченная история сохраняется.
Частичная/полная оплата и явное закрытие используют существующие связи и версии;
закрытие после частичной оплаты не создаёт новую проводку.

V33 добавляет [полное редактирование правил](full-rule-editing.md): ruleName,
замену определения при replaceDetails=true и пересчёт будущих несвязанных экземпляров.

## Выпуск и проверки

По уточнению владельца от 2026-11-04 старых клиентов нет, Android ещё разрабатывается.
Дополнительная минимальная версия и capability для `ONCE` не вводятся.
Выпуск синхронизируемых бюджетов требует согласованного backend с V32 и Android,
понимающего `ONCE`, в том числе у всех участников общего бюджета.
Существующая capability `confirmedPlanLinkingV1` действует независимо, без изменений.

Автоматические проверки покрывают диапазоны расписаний, границу суток `Asia/Almaty`,
создание через API use case и Firebase HTTP, отсутствующий/null `scheduleValue`,
задержанную доставку v2/v4, повтор requestId, sync-данные, изменение суммы,
частичную/полную оплату, закрытие, деактивацию, конкурентную доставку и расширение горизонта.
Миграционный тест проверяет чистую схему и V31 → V32 с сохранением прежней строки.
Проверка схемы учитывает, что nullable столбец требует явного `IS NOT NULL` для
регулярных расписаний: [документация PostgreSQL 17](https://www.postgresql.org/docs/17/ddl-constraints.html).
Развёртывание и проверка реальным Android-клиентом выполняются отдельно.

Проверка 2026-11-04: `./gradlew check bootJar` успешна — 326 unit и 271 integration-тест
без ошибок и пропусков, PostgreSQL/Testcontainers, ktlint, Detekt, JaCoCo и сборка JAR.
