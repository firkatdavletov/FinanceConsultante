# Тестировщик Kotlin / Spring Boot

## Контекст и стратегия

Прочитай [AGENTS.md](../../../AGENTS.md), критерии выбранной задачи в [PLANS.md](../../../PLANS.md) и применимые разделы [ARCHITECTURE.md](../../../ARCHITECTURE.md). Ожидаемый результат выводи из пользовательского сценария и финансовых правил, а не копированием алгоритма реализации в тест.

Сначала определи риск: неправильная сумма, дубль/потеря записи, доступ к чужому бюджету, неверная дата/период, повторное списание резерва или потеря отчёта. Составь небольшой набор проверок, который отличает правильное поведение от этих ошибок. Не увеличивай число тестов ради количества.

## Уровни проверок

| Уровень | Что проверять | Инструменты |
| --- | --- | --- |
| Unit | Money, parser, категории, лимит, даты, прогноз, правила состояний | JUnit Jupiter + kotlin-test/AssertJ, `Clock.fixed`, без Spring |
| Application | Проверки прав и переходов, работа портов, решение об уточнении | Простые fake-порты; MockK при необходимости, без мокирования каждого внутреннего вызова |
| Persistence | Flyway, реальные SQL-агрегаты, unique/FK/check, транзакции и конкуренция | Testcontainers PostgreSQL той же major-версии, что в production |
| HTTP contract | Telegram и OpenAI JSON, ответы API, ошибки, timeout/retry | WireMock с фиктивными credentials и запретом внешней сети |
| Spring wiring | Конфигурация, профили, биндинг настроек, соединение адаптеров | Spring test slice или ограниченный `@SpringBootTest` |
| Сквозной | Update → inbox → use case → ledger/outbox → фальшивый Telegram | Testcontainers + HTTP stub; отдельная integrationTest-задача после T01 |

Интеграционные тесты входят в `check` после настройки T01. Отсутствие Docker не повод подменять PostgreSQL H2 или объявлять SQL-проверки пройденными. Реальные Telegram/OpenAI вызовы и расходы API не входят в обычный CI.

## Финансовые контрольные сценарии

- Начальный остаток 0; доход 1 300 000; расходы 15 000, 700 и 1 300 → остаток **1 283 000**, расходы **17 000**, продукты **15 700**, здоровье **1 300**. Повтор каждого update сохраняет итог.
- `700`, `700.0`, `700,00` равны как деньги; дробные сотые сохраняются; лишняя точность, overflow, нулевая сумма и неподдерживаемая валюта отклоняются. Отрицательный баланс сохраняется и отображается.
- Из расхода 1 300 возвращено 300 → чистый расход 1 000. Возврат не становится обычным доходом. Отмена и исправление меняют итог один раз и сохраняют аудит.
- B = 300 000, R = 100 000, E = 50 000, G = 30 000, D = 10 → F = 120 000, лимит **12 000**. При G = 0 → **15 000**. После связанной оплаты 20 000 B и R уменьшаются одинаково, F остаётся прежним.
- Резерв для цели не меняет B; оплата покупки из этого резерва уменьшает B и G без двойного вычета. Неоплаченный план и ожидаемая зарплата не являются проводками.
- При F < 0 лимит 0 и показан дефицит; при неполной настройке нет уверенного заключения о доступных тратах. Последний день месяца даёт D = 1, а не 0.

## Сбои и пограничные случаи

Выбирай применимые к изменению сценарии:

- Два одновременных подтверждения, конфликт версии, повтор отмены, доступ по чужому entry/draft ID.
- Остановка до commit inbox; после commit до продвижения offset; после ledger commit до ответа; после успешного `sendMessage` до сохранения SENT. В последнем случае проверять отсутствие дубля денег, не обещать exactly-once отправку.
- Истёкший lease, рестарт worker, повтор scheduler tick, смена timezone, совпадение недельной и месячной рассылки, выход за окно catch-up.
- Граница `[start, end)`, UTC vs Asia/Almaty, високосный февраль, обязательство на 31-е число, поздний ввод и исправление старой записи.
- Пустой прошлый период, возвраты больше расходов текущего периода, неполный месяц и дни без трат в среднем. Проценты не вычисляются делением на ноль.
- Неверный JSON, незнакомая категория, выдуманная сумма, отказ модели, неполный ответ, 429/5xx, timeout, лимит бюджета API, отключённый AI, prompt injection.
- Чужой пользователь не читает данные и не вызывает AI; после T16 отзыв доступа действует на уже поставленные в очередь отчёты.

Для конкуренции используй независимые соединения/транзакции и управляемые барьеры: два последовательных вызова не доказывают отсутствие гонки. Для таймеров используй внедрённое время и ограниченное ожидание условия; `Thread.sleep` на минуты делает тест хрупким. Для scheduler/outbox не прячь весь тест внутри внешней rollback-транзакции: это может скрыть реальные commit-границы.

Проверка миграции включает пустую БД и, когда схема изменяется, БД предыдущей версии с синтетическими строками. Backup оценивается восстановлением в отдельную БД и сверкой данных; наличие файла дампа не подтверждает восстановимость.

## Как завершать проверку

Сопоставь выполненные проверки с критериями задачи. При дефекте укажи минимальное воспроизведение, ожидаемое и фактическое поведение, влияние и место в коде. Разделяй ошибку продукта, ошибку теста и ограничение окружения.

Финальный результат содержит вердикт по проверенному объёму, команды и исходы, найденные дефекты и непроверенные критерии. Не требуй произвольного процента покрытия как замену денежных и интеграционных проверок. Для обратимых правок документации ограничься валидностью навыков, ссылками и согласованностью, без тестов формулировок.
