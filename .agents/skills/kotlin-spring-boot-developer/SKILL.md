# Разработчик Kotlin / Spring Boot

## Контекст

Работай в рамках [AGENTS.md](../../../AGENTS.md) и выбранной задачи [PLANS.md](../../../PLANS.md). Перед реализацией прочитай [ARCHITECTURE.md](../../../ARCHITECTURE.md): там целевая архитектура, code style, деньги, даты, идемпотентность и интеграционные границы. Не копируй эти правила в новые документы. [CONTEXT.md](../../../CONTEXT.md) отделяет уже реализованное от запланированного.

## Рабочий процесс

1. Найди существующий use case и его входы/выходы. Сопоставь требуемый результат с критериями задачи. Если задача ещё не имеет нужных зависимостей, выполни разрешённую часть и укажи конкретную недостающую зависимость.
2. Выбери минимальный вертикальный срез: вход → проверка → доменное решение → хранение → ответ. Для простого изменения не создавай новый слой или модуль. Для финансового изменения сначала определи поведение при повторном вызове и частичном сбое.
3. Реализуй доменную логику независимо от Spring. В application-сервисе координируй сценарий и транзакцию; SQL/HTTP остаются в адаптерах. Подключай только действительно используемые зависимости совместимых версий.
4. Если меняется схема, добавь следующую Flyway-миграцию и проверку сохранения существующих данных. Для нового обязательного поля явно определи backfill старых записей. Не меняй уже применённую миграцию.
5. Добавь проверки по риску изменения, используя [навык тестировщика](../kotlin-spring-boot-tester/SKILL.md). Исправление ошибки сопровождается регрессионной проверкой, которая обнаруживает исходный дефект.
6. Проверь diff, запусти подходящие задачи сборки, обнови фактическую документацию и статус плана. Укажи наблюдаемый результат и оставшиеся ограничения.

## Решения на границах

| Изменение | Что обязательно продумать |
| --- | --- |
| Новая операция / корректировка | Деньги и валюта, начало учёта, источник идемпотентности, права, аудит, повтор callback, optimistic locking |
| SQL и миграция | Принадлежность household, FK/unique/check, rollback, индексы для действительного запроса, совместимость существующих строк |
| Telegram handler | Автор и private chat до доступа к данным, состояние диалога после рестарта, экранирование текста, размер ответа |
| OpenAI | Версия schema/prompt, проверка семантики ответа, подтверждение AI-черновика в MVP, timeout и fallback |
| Лимит / прогноз | Какие величины — факт, план или резерв; отсутствие двойного учёта; явные параметры и контрольный пример |
| Расписание | Локальная дата/период, уникальный job, lease, catch-up, outbox и неоднозначный сетевой результат |

Уникальность обеспечивается ограничением БД, а не только `exists()` перед `insert`. При обработке конфликта используй операцию вроде `INSERT ... ON CONFLICT` либо корректную транзакционную границу; после SQL-ошибки нельзя продолжать PostgreSQL-транзакцию как успешную. Подтверждение двух конкурирующих callback даёт одну финансовую запись.

Внешний вызов не помещай внутрь долгой `@Transactional`-операции. Для ответа на уже записанный расход используй outbox; сбой Telegram не должен откатывать успешно учтённую трату. Сохрани готовый ответ и версию среза, чтобы retry не пересчитывал деньги или AI-текст незаметно.

При изменении финансовой записи инвалидируй зависимые дневные снимки/кэши. Если ответ содержит итог бюджета, вычисляй его согласованно с записью: конкурентный use case не должен показывать баланс из несогласованных чтений.

## Проверка и результат

Сначала запускай затронутые тесты, затем доступный `./gradlew check` и `./gradlew bootJar` для завершённого изменения приложения. До T01 не называй отсутствующие задачи linters/integrationTest существующими. Для изменений только Markdown используй проверку ссылок/структуры без сборки JVM.

Не добавляй production-workaround ради прохождения теста, не ослабляй инвариант и не пропускай неуспешные проверки. Если нужны Docker, сеть или секрет, отдельно укажи, какой сценарий не проверен; локальные unit-тесты выполни независимо от этого.

Результат работы: работающий сценарий в пределах поручения, необходимые миграции/проверки, список выполненных команд и их исходов, актуальный статус задачи. Переносы архитектуры и смену технологий объясни причиной, существенной для проекта.
