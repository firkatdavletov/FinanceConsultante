# Дебаггер Kotlin / Spring Boot

## От симптома к причине

Прочитай [AGENTS.md](../../../AGENTS.md), [CONTEXT.md](../../../CONTEXT.md) и соответствующую границу в [ARCHITECTURE.md](../../../ARCHITECTURE.md). Не считай запланированный компонент реализованным: сначала проверь код и конфигурацию.

1. Зафиксируй симптом, ожидаемое поведение, шаги, среду, время с timezone, версию приложения и частоту сбоя. Для денежного дефекта запиши синтетический пример начального остатка и операций, на котором видно расхождение.
2. Воспроизведи минимально: unit-тест для расчёта, Testcontainers для SQL/гонки, HTTP stub для API, local/test-профиль для wiring. Не запускай второй poller с production-токеном ради диагностики.
3. Собери только нужные факты: stacktrace без секретов, цепочку причин, состояние inbox/draft/ledger/outbox, применённые миграции, effective config без credentials. Сопоставь их по техническому correlation ID. Не копируй полные финансовые сообщения или dump в отчёт.
4. Сформулируй проверяемую гипотезу и проверь на одной границе за раз. Разделяй ошибку приложения, некорректный ввод, недоступность внешней системы и проблему окружения. Не исправляй сразу несколько предполагаемых причин без свидетельств.
5. Для подтверждённой причины внеси минимальное исправление по [навыку разработчика](../kotlin-spring-boot-developer/SKILL.md), добавь регрессионную проверку по [навыку тестировщика](../kotlin-spring-boot-tester/SKILL.md) и проверь соседний критический сценарий.
6. Удали временные логи и диагностические обходы. Опиши первопричину, исправление, результаты проверок и отдельно — требуется ли восстановление уже повреждённых данных.

## Карта диагностики

| Симптом | Проверить в первую очередь |
| --- | --- |
| Не запускается приложение | Фактический JDK и Wrapper, dependency resolution, active profile, обязательные properties, корневой `Caused by`, подключение БД/Flyway |
| Bean не найден / транзакция не действует | Component scan базового пакета, constructor injection, conditional configuration, proxy/self-invocation, нужный transaction manager |
| Неверный баланс | Начало учёта, opening balance вне доходов, типы/scale, POSTED/VOIDED, refunds, дубли источника, границы времени и household |
| Вдвое уменьшился лимит | Оплата одновременно осталась в R, цель учтена в E и G, план взноса вычтен как реальные деньги, регулярный расход включён в переменное среднее |
| Дублируются расходы | DB unique для источника, два poller/worker, lease, повтор callback, запись до фиксации inbox, источник сменился с draft на callback |
| Пропали сообщения | Offset продвинут до commit, пропущен элемент batch, истёк срок хранения updates Telegram, FAILED без видимого восстановления |
| Дублируются только ответы | Outbox business key, число попыток, неоднозначный исход `sendMessage`, рестарт между отправкой и SENT; отдельно убедиться, что ledger не задвоен |
| Не приходит утренний отчёт | Timezone бюджета, `Clock`, срок job, окно catch-up, lease, очередь outbox, живой процесс/засыпание хостинга, Telegram block/429 |
| Ошибки Telegram | Ответ Bot API и статус, конфликт polling/webhook, неверный токен, chat/user ID типа Long, экранирование, размер текста, `retry_after` |
| Ошибки OpenAI | Model ID, версия SDK/schema, completed/refusal/incomplete, timeout, бюджет/квота, встроенные retries, fallback и конфигурация без вывода ключа |
| Flyway / SQL | История миграций и checksum, схема предыдущей версии, типы numeric/timestamptz, FK/unique, транзакционное состояние после ошибки |
| Падение тестов | Разница JDK/профиля, отсутствие Docker, загрязнение фикстур, случайное время, реальные сетевые вызовы; не объявлять продукт исправным лишь потому, что сбой инфраструктурный |

При спорном денежном результате пересчитай баланс из первичных POSTED-записей и сопоставь с ответом/кэшем. Используй read-only запросы с фильтром household; раздели первичные данные, ошибку агрегата и устаревший снимок. Не «исправляй баланс» новой произвольной доходной записью.

При transient-сбое проверь backoff, предел попыток и восстановление после истечения lease. Бесконечный retry, увеличение timeout без причины и отключение уникальности/валидации не устраняют дефект. Для воспроизведения гонки нужны независимые транзакции и управляемая точка пересечения, а не многократный последовательный запуск.

## Данные и границы вмешательства

Обычную диагностику и регрессионные тесты выполняй локально на синтетических данных. Не удаляй volume PostgreSQL, не переписывай историю Flyway и не повторяй production-update в реальном чате как способ проверки.

Если данные уже повреждены, отдельно подготовь конкретное восстановление: какие строки затронуты, инвариант до/после, резервная копия, проверяемый SQL/миграция и способ проверить результат. Применение к production выполняется только в пределах явно порученного восстановления. Исправление кода само по себе не означает, что исторические суммы уже восстановлены.

При отсутствии доступа или необходимого артефакта выполни доступные проверки, затем назови ровно то, что нужно для проверки оставшейся гипотезы. Не проси секреты в переписке и не выдавай предположение за установленную первопричину.

## Итог

Сообщи: симптом → подтверждённая причина → что исправлено → чем проверено. Если причину установить не удалось, перечисли оставшиеся гипотезы и конкретное свидетельство, которое их различит. В плане отмечай завершённой только фактически устранённую и проверенную часть.
