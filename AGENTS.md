# Инструкции Codex для FinanceConsultante

## Назначение

Развивай личного Telegram-бота для учёта доходов, расходов и семейного бюджета на Kotlin / Spring Boot. Отвечай пользователю по-русски; имена программных сущностей пиши по-английски. Сохраняй существующее имя проекта и базовый пакет `com.firkatdavletov.financeconsultante`.

## Что читать

1. [CONTEXT.md](CONTEXT.md) — назначение, границы продукта, текущее состояние и рабочие предположения.
2. [ARCHITECTURE.md](ARCHITECTURE.md) — единый источник архитектуры, финансовых инвариантов и code style.
3. Ролевой навык, соответствующий работе:

| Работа | Навык |
| --- | --- |
| Реализация функции, рефакторинг, миграция БД | [kotlin-spring-boot-developer](.agents/skills/kotlin-spring-boot-developer/SKILL.md) |
| Разработка тестов, проверка приёмки, регрессия | [kotlin-spring-boot-tester](.agents/skills/kotlin-spring-boot-tester/SKILL.md) |
| Воспроизведение ошибки, диагностика, исправление сбоя | [kotlin-spring-boot-debugger](.agents/skills/kotlin-spring-boot-debugger/SKILL.md) |

Роли описывают способы работы одного агента; наличие трёх навыков само по себе не требует запуска субагентов. При исправлении ошибки сначала используй debugger, затем developer и tester по необходимости. Не загружай инструкции нерелевантной роли.

`ARCHITECTURE.md` — общий проектный документ. Обнаруживаемые Codex навыки лежат в `.agents/skills/<name>/SKILL.md` и имеют YAML-поля `name` и `description`. Если навык ещё не появился в интерфейсе текущей сессии, прочитай его по ссылке из этой таблицы. Формат описан в [документации Codex](https://learn.chatgpt.com/docs/build-skills).

## Порядок работы

- Перед изменениями проверь `git status --short`, существующий код, конфигурацию сборки и более локальные `AGENTS.md`. Сохраняй пользовательские изменения, включая уже staged-файлы.
- Выполняй запрошенный объём и не начинай новый backlog автоматически.
- Если запрос содержит ID задачи, укажи его и ожидаемый результат. Существенные неопределённости уточняй, а обратимые технические решения принимай самостоятельно и кратко фиксируй.
- Реализуй законченный сценарий вместе с обработкой ошибок и необходимыми проверками. Не добавляй зависимости, абстракции и инфраструктуру для гипотетических потребностей.
- Для новых или меняющихся API сверяй официальную документацию и совместимость с версиями проекта. Не подставляй примеры Spring Boot 3 в Spring Boot 4 без проверки.
- После изменений выполни подходящие проверки. Отдельно сообщи о непроверенном: отсутствие Docker, JDK, сети или ключей не означает успешный тест.
- Обновляй `CONTEXT.md`, когда изменилось фактическое состояние или принято продуктовое решение; `ARCHITECTURE.md` — при изменении архитектуры. Не дублируй историю каждой правки во всех документах.

## Обязательные ограничения

- Деньги, баланс, лимиты и прогнозы рассчитываются детерминированным Kotlin-кодом. Ответ LLM является недоверенным предложением и проходит проверку перед записью.
- Проверка активного членства Telegram-пользователя предшествует доступу к финансовым данным и вызову OpenAI. Разрешены OWNER/MEMBER только в личном чате.
- Повторный Telegram update или callback не должен повторно менять бюджет. Транзакции и ограничения уникальности БД обязательны на границах записи.
- Не используй `Double` / `Float` для денежных величин. Не учитывай ожидаемый доход как уже полученный, а резервирование накоплений как расход.
- Не сохраняй секреты, полные Telegram-сообщения или финансовые данные в логах, тестовых фикстурах и документации. Для тестов используй синтетические данные.
- Не вызывай реальные OpenAI / Telegram API из обычных тестов. Проверки с реальным ботом или платным API должны быть явно выбраны пользователем и выполняться отдельно от CI.
- Не изменяй production-данные, не удаляй тома БД и не отправляй пробные сообщения без соответствующего поручения. Пользовательский запрос на развёртывание или отправку учитывай как разрешение в пределах его объёма.

## Проверки и готовность

Существующие команды запускаются из корня репозитория через Gradle Wrapper:

```bash
./gradlew test
./gradlew check
./gradlew bootJar
```

`check` включает `test`, `integrationTest`, `ktlintCheck`, `detekt` и общий `jacocoTestReport`. Форматирование применяется отдельной командой `./gradlew ktlintFormat`. Интеграционные тесты находятся в `src/integrationTest/kotlin`; unit-тесты добавляются в `src/test/kotlin`. Не называй `test NO-SOURCE` выполненными unit-тестами: до реализации домена этот набор пуст.

Для задач Gradle типа `Test` профиль принудительно задан как `test`, флаги Telegram/OpenAI/уведомлений выключены system properties. Новые адаптеры должны учитывать эти флаги. PostgreSQL/Testcontainers подключены в T02; отсутствие Docker не должно превращаться в автоматический skip или fallback таких тестов. Отдельный локальный PostgreSQL разрешается выбирать только явным тестовым параметром из README; это не подтверждает проверку контейнерного окружения. Команды запуска, профили и отчёты описаны в [README.md](README.md).

Для изменения только Markdown достаточно проверить ссылки, согласованность документов и формат навыков; сборка приложения не нужна. Для изменения поведения проверяй затронутый сценарий, финансовые инварианты, миграции и сбои внешних систем по применимости.

Задача завершена, когда выполнены её критерии приёмки, изменения проверены, документация соответствует реализации, секретов в diff нет. Финальный ответ: что изменено, какие проверки выполнены и какие ограничения остались. Не выполняй commit, push или deploy только потому, что задача помечена `DONE`.
